## 1. Goals, Locked Decisions & Explicit Deviations

1. **Top-level connections only in Object Explorer:** `mod+click` (`Ctrl+Click` on Windows/Linux, `⌘+Click` on macOS) multi-selects top-level connection roots (`node.parent === 0`, `kind === 'server'` for both SQL Server and BigQuery; engine resolved via `explorerNodeProvider(target)`). Registered with `place: 'serverRow'` so it never clashes with `explorer.openPeekTab` (`place: undefined`).
2. **Engine-homogeneity lock on `Ctrl+Click`:** Selecting a SQL Server connection first locks subsequent `mod+click` picks to SQL Server connections (and vice versa for BigQuery). Incompatible rows dim using `--varia-disabledForeground` (passing WCAG AA contrast; never low-opacity text).
3. **Run Mode Prompt at every multi-target same-engine execution (`>= 2` enabled targets):**
   - **Coordinated Transaction (All succeed or all roll back)** — cross-platform coordinated local/session transactions (no MSDTC).
   - **Fire and Forget (Independent execution, no rollback)** — parallel by default, with optional **Sequential rollout (stop on first error)**.
   - **BigQuery permanent DDL guard:** When GoogleSQL contains permanent DDL, Transaction mode is disabled with an explanation, and **Pre-flight Dry Run (free) + Sequential stop-on-first-error** is pre-selected.
   - **Single-enabled-target shortcut:** If a user unchecks targets in a same-engine multi-server tab down to **1** enabled target, Execute skips the Coordinated Transaction vs Fire-and-Forget prompt (still applying BigQuery's cost threshold prompt if applicable) and runs directly as an ephemeral single-target execution.
4. **Mixed DDL / DML + multi-statement `SELECT` support:** A **Summary** tab (and Stacked Summary band) coexists alongside **Combined**, per-server result tabs, and **Differences** (and renders even on pure-DDL/DML runs with zero `SELECT` sets). Rolled-back runs keep already-streamed `SELECT` rows inspectable under an amber **"Rolled back — preview only (not committed)"** notice.
5. **Automatic `Combined` view:** Built in the backend **after Phase 2 settles** whenever `>= 2` targets return in-memory rows for a statement slot and the merged result fits within the remaining query budget without evicting or truncating individual server results. Stored as `kind: 'combined'` (supporting Sort, Filter, Pivot, Transpose, Column Profile, Search, Copy, and Save Results As).
6. **Cross-Engine (`SQL Server` + `BigQuery`) non-DDL (`SELECT`) from day one:** Dual-dialect split editor (`Transact-SQL` | `GoogleSQL`) plus single-file `-- #Dialect="sqlserver"` / `-- #Dialect="bigquery"` serialization, guarded across 3 layers (renderer allowlist lexer/Monaco diagnostics, pre-execute refusal, and backend `TSql180Parser` full-AST read-only visitor + BigQuery free Dry Run `statementType === "SELECT"`).
7. **Calm Pro polish:** Zero left-border accent rails on cards, server headers, or stacked groups. All CSS uses real `--varia-*` tokens registered in `src/shared/theme/registry.ts` with contrast pairs in `contrast-pairs.ts`, `STAGING` (not `STAGE`) environment tags, and passes `tests/theme-css.test.ts`, `tests/theme-contrast.test.ts`, `tests/grid-lint.test.ts`, and `tests/gesture-lint.test.ts`.
8. **Explicit design deviations / platform constraints (documented upfront):**
   - **Static Explorer context-menu labels (no `(N)` count in menus):** Per `CLAUDE.md` and `tests/context-menu-template.test.ts`, macOS native context menus are built exclusively in main from `commandCatalog` without renderer-supplied dynamic text. Context menu items use crisp static titles (`New Multi-Server Query`, `New Cross-Engine SELECT…`, `Refresh Selected`, `Disconnect Selected`, `Clear Selection`), while the live count (`"3 SQL Servers selected"`) shows in Object Explorer's `26 px` multi-select header bar.
   - **Cross-Engine BigQuery is single-statement `SELECT` only:** BigQuery's free `dryRun: true` returns `statementType == "SCRIPT"` for any multi-statement script (even `SELECT 1; SELECT 2;`), preventing authoritative read-only verification on multi-statement BigQuery scripts. Cross-Engine mode therefore enforces single-statement `SELECT` / `WITH` on BigQuery (and read-only `SELECT` / `WITH` AST allowlist on SQL Server).
   - **Ephemeral per-run sessions (no persistent idle transactions across runs):** Multi-server runs open fresh unpooled SQL Server connections / BigQuery DML sessions per run and close them at run end so idle locks, temp tables, and BigQuery session storage never leak across N servers or complicate single-server Disconnect.
   - **No "Leave it running" (`detach`) or persistent `jobKey` on multi-target BigQuery runs:** Detaching a BigQuery job inside a coordinated transaction would leave table locks open for 24 hours. Multi-target tabs never persist `jobKey` and are excluded from `holdsJob()` / `canCloseRunningJob()` / `keptQueries`: Close/Disconnect/Quit always prompt to cancel running multi-target jobs via `query.cancel`. Each `query.executeMulti` execution generates a fresh ephemeral `jobKey` so crash/shutdown orphans automatically surface in Varia's existing `reviewJobsWithoutTab` flow grouped by project.
   - **Unzoned `date`/`datetime` + zoned `timestamp` widen to `text` in `Combined`:** Merging an unzoned SQL Server `datetime` with a zoned BigQuery `TIMESTAMP` into `timestamp` would silently inject the workstation's local timezone; `ResultCombiner` widens that pair to `text` instead so no fabricated UTC offsets appear.
   - **Reuse `query.cancel` (no separate `query.cancelMulti`):** Multi-server runs register their `queryId` with existing `query.cancel` so `earlyStops` and `supervisor.drainingFor` work identically with zero duplication.

## 4. Backend Execution Architecture

### 4.1 Ephemeral Per-Run Sessions, `SESSION_BUSY` Gate & Concurrency Caps
- **Shared per-`sessionId` active-run gate (`SqlService.cs`):** `ResultStore.BeginQuery(sessionId)` does not enforce `SESSION_BUSY` on its own. Guard both `query.execute` and `query.executeMulti` with a shared active-session map (`TryAdd(sessionId, queryId)`) **before** calling `store.BeginQuery(sessionId)` so concurrent runs on the same tab reliably throw `SESSION_BUSY` without wiping prior results.
- Every `query.executeMulti` run opens fresh ephemeral sessions and disposes them at run end:
  - **SQL Server:** Uses `CreateConnection(id, database, stateful: true)` (unpooled, `Pooling = false`, `ConnectRetryCount = 0`) + `SessionPrologue` (preserving full identity verification / SID & Entra OID pinning). Accounted against a global cap (max **8 concurrent multi-server runs** and **64 active ephemeral SQL connections**, checked against `SessionLimit`).
  - **BigQuery:** Holds `connection.Lease()` for every participating `BigQueryConnection` during the run. DML Transaction runs create a fresh session (`createSession: true`) after resolving location; pure `SELECT` / Fire-and-Forget DDL runs create no BigQuery session.
- **Disconnect & Shutdown integration (`SqlService.cs`):**
  - `RunningQuery` tracks `IReadOnlySet<string> ConnectionIds` so disconnecting any participating server cancels the multi-run cleanly.
  - Separate `bool AbandonBigQueryOnShutdown` from `bool Detachable` on `RunningQuery` (`SqlService.cs:134-161`): multi-runs set `Detachable = false` (so `query.cancel({ detach: true })` is refused) and `AbandonBigQueryOnShutdown = hasBigQuery`, and `BeginShutdown()` (`SqlService.cs:3416`) checks `if (query.Detachable || query.AbandonBigQueryOnShutdown) query.Abandon();` — so shutdown cleanly abandons BigQuery HTTP calls (never racing `bigQuery.Dispose()` after `DrainTimeout = 1500 ms`; surviving jobs surface in `reviewJobsWithoutTab`) while cancelling/rolling back SQL Server targets cleanly.

### 4.2 Coordinated Two-Stage Barrier (`MultiQueryCoordinator.cs`, `SqlServerMultiRunner.cs`, `BigQueryMultiRunner.cs`)
1. **Pre-flight stage:**
   - **Cross-Engine (`crossEngineReadOnly`):** Validate T-SQL with `IReadOnlySqlValidator` (`ReadOnlySqlValidator.cs`, `TSql180Parser` in ONE `ResultNames.OnParseThreadAsync` call per request) AND BigQuery with `GoogleSqlScanner.IsReadOnlySelect` + free `dryRun: true` through `MetadataAsync` (`BigQueryRateLimiter`) with resolved dataset location asserting `estimate.Faked || estimate.StatementType == "SELECT"`. Any violation aborts immediately (`READ_ONLY_VIOLATION`, 0 queries executed).
   - **BigQuery `preflightDryRun`:** Expose `Location` on `BigQueryEstimate` (`BigQueryService.cs:207,406,455`) and route `DryRunAsync` + `TabLocationAsync` through `MetadataAsync`. Free `dryRun: true` across all BigQuery targets with resolved dataset location. Any failure marks peers `skipped` and returns immediately (\$0 billed, 0 mutations). Multi-statement BigQuery scripts honestly report `incomplete: 'script'` if dry-run stops at DDL.
   - **SQL Server Transaction pre-flight:**
     - Reject duplicate physical servers (`SqlService.ServerOf(connectionId)`) in Transaction mode (prevents undetectable client-side self-deadlock!).
     - Parse all batches inside ONE `ResultNames.OnParseThreadAsync` call: **fail closed** on `MaxParseChars`, `MaxParenDepth`, or syntax errors (`errors.Count > 0`); reject explicit `CommitTransactionStatement` / `RollbackTransactionStatement` (without savepoint) AND the full Msg 226/574 non-transactional statement list (`Create/Alter/DropDatabase`, `Backup/Restore`, `Reconfigure`, `Dbcc`, Full-Text DDL, Availability Group DDL, `AlterServerConfiguration`, Resource Pool DDL, `Shutdown`, `Kill`).
   - **BigQuery Transaction pre-flight:**
     - Refuse cleanly in emulator mode (`Emulator == true`).
     - Reject permanent DDL, explicit `BEGIN/COMMIT/ROLLBACK TRANSACTION`, `EXECUTE IMMEDIATE`, `CALL`, **`EXPORT DATA`**, and **`LOAD DATA`** via `GoogleSqlScanner` (preventing dynamic SQL, stored procedures, or irreversible GCS exports from escaping rollback).
     - Resolve every target's location *before* `BEGIN TRANSACTION` via `MetadataAsync` (dataset via `TabLocationAsync`, connection `Location`, or single-statement free `dryRun`'s `estimate.Location`). For multi-statement scripts with `location: Automatic` and no default dataset, fail pre-flight with clear guidance asking for a default dataset or explicit location (since dry-run defaults to `US`).
2. **Phase 1 (Execution):**
   - Parallel (`SemaphoreSlim(min(targets.Count, 8))`) or sequential (`sequential: true`, stopping on first error and marking remaining targets `skipped`).
   - **SQL Server Transaction mode:**
     - Gate `CURRENT_TRANSACTION_ID()` on `profile.Major >= 13 || profile.EngineEdition is 5 or 8` (covers SQL Server 2016+ AND Azure SQL Database / Managed Instance which report `ProductMajorVersion == 12`; falls back to `XACT_STATE() == 1 && @@TRANCOUNT >= 1` on on-prem 2012/2014).
     - Executes `SET XACT_ABORT ON; BEGIN TRANSACTION;` + `SELECT CURRENT_TRANSACTION_ID()` (when supported).
     - After **every batch**: temporarily resets `connection.FireInfoMessageEventOnUserErrors = false` and detaches `onInfo` (preventing `SET STATISTICS TIME/IO ON` from leaking probe stats into Messages) before running the dedicated 3-column probe (`SELECT XACT_STATE(), @@TRANCOUNT, CURRENT_TRANSACTION_ID()` — or 2-column on 2012/2014). Validates `reader.FieldCount` and `reader.GetFieldType(...)` (`short`, `int`, `long`) BEFORE reading (so `SET SHOWPLAN_XML/TEXT/ALL ON` returning 1 string column cleanly aborts Phase 1 instead of throwing `InvalidCastException`), then restores `onInfo` and `FireInfoMessageEventOnUserErrors`. Checks `Raised() == raisedBefore` (catches `SET XACT_ABORT OFF` `InfoMessage` errors).
     - Does **not** run `ExecuteAgainSql` mid-script (which would silently clear a user's `SET NOEXEC ON`); if the probe returns no rows or unexpected schema mid-script, aborts Phase 1 immediately (running `ExecuteAgainSql` only in Phase 2 rollback cleanup).
     - If `@@TRANCOUNT == 0` or `CURRENT_TRANSACTION_ID() != startTxId` without an error (e.g., `EXEC('COMMIT TRAN')`), classifies that target as **`commitInDoubt`** (never `rolledBack`) and aborts peers immediately!
   - **BigQuery Transaction mode post-Phase-1 verification:**
     - After each BigQuery transaction target completes Phase 1, apply `BigQueryService.Apply` over `ChildrenAsync(full: true)` to verify `session.Transaction == BigQueryTransaction.Open`. If any child executed `COMMIT_TRANSACTION`, classify that target as **`commitInDoubt`** and abort peers; if `session.Transaction` is `None` or `Unknown` (e.g., `children == null` or truncated listing on a script), abort peers cleanly.
   - **SQL Server Fire-and-Forget mode:** If `@@TRANCOUNT > 0` after the last batch, rolls back before disposing the ephemeral connection and logs an info warning.
   - **Fail-fast abort & barrier timeout:** Any target failure, timeout, connection loss, or `query.cancel` cancels all active peers' Phase 1 tokens and releases the barrier with `Abort`. In Transaction mode, enforce a bounded barrier cap (default 300 s when `timeoutSeconds == 0`) so PROD locks cannot hang forever.
3. **Phase 2 (Commit or Rollback):**
   - **Commit (all targets passed Phase 1):**
     - SQL Server: resets `connection.FireInfoMessageEventOnUserErrors = false`, runs `WHILE @@TRANCOUNT > 0 COMMIT TRANSACTION; SELECT @@TRANCOUNT;` in parallel (catching severity 11–16 errors as `SqlException`).
     - BigQuery: refactor `BigQueryService.Sessions.cs:643-695` into an `internal` commit core returning a structured outcome (`Committed | Refused | CancelledBeforeSend | InDoubt`, where `InDoubt` guarantees `Unknown()`/`PendingAbort()` has already started): call `token.ThrowIfCancellationRequested()` before `Jobs.Insert` and set `maySent = true` **immediately before** `Jobs.Insert` (resetting `maySent = false` only on `NotSent(error)` before retry) so mid-`Jobs.Insert` cancellation always hits `Unknown()`/`PendingAbort()`. For ephemeral multi-query sessions, call `AbortAsync` (with a fresh bounded token, calling `RememberFailedAbort` on failure) on `Committed`, `Refused`, or `CancelledBeforeSend` so the session never leaks for 24h; on `InDoubt`, mark `commitInDoubt` without calling `AbortAsync` or double-calling `PendingAbort`.
     - Any peer failing *during* `COMMIT` is marked `commitInDoubt` (never falsely claiming rollback).
   - **Rollback (any target failed/cancelled):**
     - SQL Server: uses a **fresh bounded 10 s `CancellationToken`** (never the cancelled Phase 1 token!), resets `FireInfoMessageEventOnUserErrors = false`, runs `ExecuteAgainSql` + `ROLLBACK TRANSACTION`, and always disposes the unpooled `SqlConnection` in `finally`. Marks all stored result sets of rolled-back targets `rolledBackPreview = true` (`volatile bool` on `ResultSetBuffer`) and emits non-droppable `resultSet.meta`.
     - BigQuery: cancels active jobs, waits boundedly (`SettleAsync`), calls `BigQueryService.AbortAsync` (atomic rollback + session end, calling `RememberFailedAbort` on failure).
     - Windowed BigQuery results marked `rolledBackPreview = true` construct per-target `QueryArgs` for `BigQueryWindow` and are refused for `rerun` in `PlanAuxiliary` (`SqlService.BigQuerySample.cs`).
