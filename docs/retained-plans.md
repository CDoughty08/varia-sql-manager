# Retained plans

Open **Window › Execution Plan** (or **Show Execution Plan** in the command palette), then select **Plan history**. The window automatically copies original XML from completed actual captures, SQL-returned Showplan results, and successful estimated-plan requests, whether or not their viewer was opened. Select a snapshot to browse it in the existing viewer. **Open snapshot document** opens an independent `.sqlplan` document with the usual graph/XML source views. **Save plan as…** uses the existing execution-plan save dialog (`.sqlplan` or `.xml`) directly, including for XML too large to fill an editor in one frame.

**Pin snapshot** protects an entry from automatic eviction. **Remove snapshot** removes the selected entry, including a pin. **Clear unpinned** preserves pins; **Clear all snapshots** removes pins too. Both clear actions cancel pending history copies. Removing history entries leaves already opened documents and saved files usable. Edits to an opened document do not change its snapshot.

Snapshots belong to this workbench window, across every query tab. Re-executing a query, closing its results or tab, disconnecting, losing/restarting the SQL backend, hiding/closing the Execution Plan pane, and parser/layout/GPU cache eviction do not clear acquired XML. Closing/reloading the workbench window clears all history, including pins. History is not included in hot exit or recovery. Save XML explicitly for persistence. Popout panes use their owning window's service; independent workbench windows have separate history.

Saved files contain the original XML; history metadata and pin state are not added to Showplan XML. Preparing a graph requires the existing backend parser; XML source and file saving remain available while it is unavailable.

## Metadata and provenance

Each snapshot records its original source key, capture type, batch/repetition and result row when known; execution and tab identities; source document name/path; server/connection identity; requested and reported final database; execution timestamps, elapsed time, session SPID/login and batch counts when available; and the SQL submitted to that request, with its starting editor line and selection/document scope. Metadata is copied at request start and completion, so editing SQL, renaming a tab, or changing its database later does not rewrite history. SQL may include sensitive literals, just as the original plan may; history remains in memory until explicitly saved.

Toolbar-captured completion XML is **Actual**, even when live capture was requested. Estimated requests are **Estimated** and represent compilation without execution. A SQL-returned result descriptor does not distinguish `SHOWPLAN_XML` from `STATISTICS XML`: these entries are **SQL-returned (capture type unspecified)** rather than guessing from runtime counters. Transient live samples are not XML documents and are not retained here.

Execution outcome is independent of document completeness. A completed statement from a cancelled, timed out, failed, lost, or completed-with-errors script retains that outcome and is labeled **Partial execution**, even if its own XML is complete. An incomplete result or truncated stored XML is labeled separately and may only be useful in XML source view. A failed estimated request supplies no documents to retain. Only metadata supplied by the existing capture is recorded; full session SET options, parameters and server environment are not reconstructed. Requested/final database does not establish the database of each statement in a `USE` batch.

## Ownership, races and budgets

- The history owns immutable XML strings and copied metadata, with no result handles, parsed models, layouts or GPU objects. Entries preserve the source keys used by the original actual/estimated viewer; snapshot IDs provide separate viewer identities.
- There are at most **32 entries** and **64 MiB** of accounted UTF-16 XML/SQL/metadata payload, including a bookkeeping allowance per entry. Oldest unpinned entries are evicted first. Pins consume the same budgets. If pinned entries leave insufficient room, new entries are rejected with a history notice; pinned entries are never silently evicted. A single XML document also has the existing **8,388,608-character** limit. Query-returned cells retain their existing storage cap.
- At most **64 documents per execution** are acquired, with at most **two acquisitions** in progress per window, each reading one source at a time. Additional concurrent completions are skipped with a notice, without a waiting queue. Each acquisition has a **five-second** total deadline. A stopped acquisition still occupies its slot until its underlying reader acknowledges cancellation or otherwise settles; repeated timeouts and clears cannot accumulate unbounded abandoned reads. At most two document reads (each up to the per-document limit, approximately 16 MiB UTF-16) are in flight, independently of stored history. Existing result/estimate buffers retain their own budgets during this interval.
- A query remains reserved until its bounded XML copy settles: the next F5 cannot cause backend `BeginQuery` to release XML before it is copied. Closing results or the query tab during a copy releases its handles after the copy settles; late completion does not recreate the closed tab/results. Closing a tab before its execution has completed abandons its still-running output as before and creates no new history acquisition.
- Backend loss during copying preserves entries already copied; unread sources fail with a history notice. Source failures are isolated, so later readable documents can still be retained. The deadline settles acquisition even if a reader fails to acknowledge cancellation. Clear/dispose invalidates pending reads; delayed responses cannot repopulate cleared history.

The history reports the most recent retention issue; it is not an audit log of every skipped source. Entry/memory limits may retain only part of an execution's documents. Snapshot history is independent of any viewer preparation/caching feature and does not implement structural or visual comparison.

## Validation

`tests/retained-plans.test.ts` exercises immutable metadata, selected SQL, automatic entry/byte eviction, pinned saturation, bounded acquisition/concurrency/deadlines, failed reads, clear/dispose races, partial/truncated provenance, re-execution reservation, close-results/close-tab races, and estimated/manual capture identities. `tests/files.test.ts` covers explicit plan-kind saving beyond ordinary SQL file limits.

Run `npm run check`, then `npm run test:retained-plans`. Set `VARIA_TEST_SQL_SERVER=localhost` for the additional real SQL Server lane (Windows integrated authentication unless SQL credentials are supplied). The Electron smoke uses isolated profiles and normal query/history/file/palette entry points to exercise actual and estimated capture, pinning, selected SQL, original XML saving after re-execution/release, cancellation, closing tabs, backend loss, reopening, removal, and window reset. The existing estimated/live plan smoke suites remain regression checks for those workflows.
