# Estimated execution plans

Use **Query › Display Estimated Execution Plan**, the query or classic toolbar's **Estimated Plan**, the editor context menu, or **Ctrl+L** (**⌘L** on macOS). A selection takes precedence over the whole editor. Connect the query first. **Cancel** stops acquisition, including compilation waiting on schema locks.

For existing session state, choose **Query › Display Estimated Plan in Query Session**, the editor context menu's same action, or **Estimate in query session** in the estimated pane. This is an explicit opt-in for each acquisition. The toolbar and Ctrl+L continue to use isolation. The pane labels the mode used for that acquisition and offers **Estimate in isolation** to switch back.

The existing **Execution plan** pane labels these results **Estimated**. Its Pixi canvas, operator outline, search, statement selection, properties, zoom and fit controls work as for actual plans. Runtime rows and timings are unavailable. **Open plan document** opens a `.sqlplan` document; the normal Save, Save As, editable XML and recovery behavior applies. Estimation keeps the last ordinary data grids and does not change **Include Actual Execution Plan**. The next ordinary execution replaces the estimate.

The output view you select is preserved when you return to the query tab or restore the output with **Ctrl+R**. A new estimate opens its plan view again, without replacing the ordinary results or statistics history.

## Session and database context

The default **isolated** mode opens a fresh, unpooled SQL connection, with connection recovery disabled, using the query's credentials, selected database and Varia's query-window SET defaults. It never borrows the tab's SQL session. This protects existing transactions, temporary objects, SET options, database context, result handles and capture options when estimation succeeds, fails, times out or is cancelled. Existing callers of `plans.estimate` that omit `mode` retain this behavior; explicit `mode: 'isolated'` is equivalent.

An isolated estimate cannot see the tab's local temporary tables, temporary procedures, prior SET changes, impersonation or uncommitted changes.

**Query session** mode (`mode: 'session'`) exclusively borrows the tab's persistent physical SQL connection through its normal session gate. A tab without a session opens one with the same one-time defaults as ordinary execution. An existing session is never reinitialized or silently reconnected. Existing local temporary objects, runtime SET options, impersonation, and uncommitted data/schema are available to compilation. The selected toolbar database is applied temporarily; both that change and standalone USE batches are restored to the session's original database. Estimation does not update the toolbar database. The returned `database` identifies the final compilation context, and optional `session` reports the SPID/login of the borrowed connection.

Neither mode executes setup SQL. Create-and-use temporary-object scripts can fail because creation is not executed. Table variables and local variables from earlier submissions are batch scoped and are unavailable even on the same connection. Dynamic SQL and stored procedures retain SQL Server's ordinary estimated-plan limitations. A statement's runtime SET, EXECUTE AS or transaction commands in the submitted selection are not executed; an estimate reflects the context already established, with SQL Server's parse-time semantics. Do not execute setup SQL merely to obtain an estimate unless you intend its effects.

Session-aware compilation is not side-effect free:

- Capture setup, preflight and cleanup overwrite `@@ROWCOUNT` and `@@ERROR`. After successful cleanup on the tested SQL Server they are both 0. These registers cannot be restored to their previous values. Keep statements that depend on them together in an ordinary execution.
- SQL Server can acquire schema locks and update optimizer statistics during compilation. Errors, deadlocks and cancellation follow SQL Server's transaction rules. In particular, cancellation of blocked compilation with **XACT_ABORT ON** rolled back the existing transaction in live validation, even though submitted SQL never executed. After cancellation or errors check `@@TRANCOUNT`/`XACT_STATE()` before continuing; do not assume the transaction survived.
- XML SHOWPLAN is subject to session TEXTSIZE. Varia temporarily raises it to avoid silently truncated XML and restores its original value, along with QUOTED_IDENTIFIER and database context, under the same cleanup budget. Other existing runtime SET options are left in force. Submitted OFFSETS and FIPS_FLAGGER tokens are conservatively refused in session mode because their parse-time state cannot be safely recovered; use isolation for those scripts.
- Existing SHOWPLAN, NOEXEC, PARSEONLY or FMTONLY settings that prevent an ordinary sentinel SELECT from executing cause refusal before Varia takes capture ownership. Those existing settings are left unchanged; turn them off explicitly or choose isolation. The preflight itself can overwrite the status registers.

The entire selection is validated before a connection opens. Existing GO parsing, repetitions, SQLCMD rejection and selection line offsets apply. A standalone `USE [database]` batch is applied through SqlClient's database-change API between compiled batches. Mixed `USE`/query batches are rejected with instructions to split at GO or choose the database in the toolbar; this prevents silently compiling in the wrong context. The query tab's database remains unchanged.

Varia turns `SHOWPLAN_XML` on in a separate batch before submitting SQL. Explicit SHOWPLAN, NOEXEC, PARSEONLY and FMTONLY tokens are conservatively rejected, even in nested statements, so a later capture toggle cannot allow submitted SQL to execute. Quoted string values and comments are ignored by this guard. A column or identifier named after one of these capture options can also be refused; estimate a selection without it. Dynamic SQL and stored procedures have SQL Server's ordinary estimated-plan limitations.

SQL Server requires the permissions needed to compile the SQL, including SHOWPLAN for referenced user databases (see [SET SHOWPLAN_XML](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-showplan-xml-transact-sql)). Unsupported engines, inaccessible databases, missing objects, syntax errors and permission errors are shown in the estimated pane. Varia does not fall back to executing the query. SQL Server compilation can still acquire schema locks and update optimizer statistics.

## Bounds and cleanup

`plans.estimate` is a unary request independent of plan streaming events and `query.execute` summaries. It has a fixed 30-second acquisition budget, a 35-second IPC deadline, at most two acquisitions in flight, 64 XML documents and 2,097,152 total XML characters. Limits fail the request with guidance to estimate a smaller selection. It does not store XML in ordinary result cells or use their truncation limits. Retained XML across tabs shares a 16,777,216-character renderer budget; older tabs report when an estimate was released and can request it again. Parsed graph limits remain those of the existing plan viewer.

Every owned capture attempts SHOWPLAN OFF using a separate two-second cleanup token. Isolated connections are always disposed. Query-session mode also verifies that a sentinel SELECT executes and restores context before releasing the session gate. Compilation failure, cancellation, timeout and size-limit errors leave the session open when cleanup succeeds, subject to SQL Server's transaction effects above. Error text distinguishes an open session from `SESSION_LOST`. A cleanup or transport failure removes and closes the borrowed session before releasing its gate: SQL Server rolls back its remaining open transaction and drops its local temporary objects. The UI clears the stale SPID and says the next ordinary execution opens a new session. A previously unfinished commit retains the existing unknown-commit-outcome warning. Varia never retries the submitted SQL or silently falls back to execution.

Cancel uses the existing query-cancel control lane with the estimate request ID; early cancellation, disconnect, session close and backend shutdown share the existing request lifecycle. No operation queues on a busy query-session gate. A running query prevents either estimate mode; session capture prevents state reads, commits and ordinary execution until it settles.

Closing a tab during estimation still checks its ordinary session for an open transaction and offers the normal commit-or-rollback decision. Cancelling that prompt keeps the estimate running. Once closing proceeds, the isolated estimate is cancelled independently; it never forces rollback of the ordinary transaction.

During query-session capture the session is busy, so closing uses the existing **running query** prompt instead of attempting to read its transaction. **Keep Running** leaves capture running. Proceeding cancels capture, waits for settlement, then closes with rollback; an active session estimate cannot be committed by the close prompt.
